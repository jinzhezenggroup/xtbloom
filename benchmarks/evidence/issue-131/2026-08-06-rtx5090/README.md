# Issue #131 CUDA active-set eigensolver compaction evidence

This directory archives the profiler and cross-over evidence for issue #131
("Compact active CUDA eigensolver buckets during SCC", a sub-issue of #80).
The exact-capacity compaction implementation itself is already on `main`
(squash history: `9c2a026` "perf: compact active CUDA eigensolver buckets",
`Refs #55, #80, #131`); this directory records the missing acceptance
evidence that issue #131 listed as outstanding: Nsight active-versus-submitted
capacity reports and measured capacity-tier cross-over thresholds for batch
sizes 1/8/32/128, homogeneous and heterogeneous, plus the Compute Sanitizer
matrix for the compacted path.

The compacted path under measurement is the reusable
`Gfn2EigensolverCompactedSolveGraph` (`src/backends/cuda/gfn2_eigensolver.cu`),
a CUDA Graph with one device-selected SWITCH per AO bucket. Each SWITCH has
bodies 0..capacity; body `k` submits cuBLAS/cuSOLVER batched work with
batchCount exactly `k`, and body 0 launches no provider arithmetic. A
single-ordered device kernel (`compact_solve_bucket_kernel`) counts the active
peers per bucket from the canonical active mask, publishes
`Gfn2EigensolverBucketActivity{active_count, submitted_eigensolver_count,
submitted_backtransform_count, completed_count}`, and sets the SWITCH
conditional through `cudaGraphSetConditional`. This telemetry is published by
the same ordered Graph launch that performs the solve, so one coherent
per-iteration active-versus-submitted report is available for every bucket.

## Workloads

The benchmark fabricates well-conditioned synthetic restricted eigensolver
batches with the same value/bucket fabrication family as the validated
`tests/cuda_eigensolver_test.cu` fixtures:

- homogeneous: one bucket, all systems `n = 32` AO;
- heterogeneous: two buckets, alternating `n = 16` and `n = 40` AO.

For each (batch size in {1, 8, 32, 128}, workload), the runner walks a
canonical active-count tier ladder from the full batch down to the empty tier
in deterministic system order, and at every tier:

1. proves correctness: the compacted Graph launch and the uncompacted
   full-capacity solve agree for every active peer (eigenvalues within
   1e-12, coefficients within 1e-10, generalized residual re-checked), and
   inactive peers stay untouched (sentinel output preserved);
2. records the per-bucket `bucket_activity` telemetry (active /
   submitted_eigensolver / submitted_backtransform / completed);
3. times both launch paths (5 warmups, 50 recorded samples,
   `cudaEvent`-time, error resets enqueued before the timed interval).

`compaction-capacity-trace.jsonl` is the raw runner output (each row is one
JSON tier measurement). `compaction-crossover-summary.csv` is the derived
flat view. Both were generated by the final committed runner source and were
not hand-edited.

## Results

### Active-versus-submitted capacity telemetry (per iteration, per bucket)

At every tier of every (batch, workload) the compacted Graph published
`active_count == submitted_eigensolver_count ==
submitted_backtransform_count == completed_count` for every bucket, i.e. the
submitted cuBLAS/cuSOLVER batch count tracks the active set exactly instead
of the fixed topology count. Rows at `active_total == 0` show all buckets at
`active = submitted = completed = 0`.

### Kernel-level proof that inactive buckets execute no eigensolver arithmetic

Nsight Systems node-level Graph tracing
(`nsys profile --trace=cuda --cuda-graph-trace=node`) of a heterogeneous
`batch = 32` Graph with 5 replays at two activity levels:

- `nsys-active0-kern_sum.csv` (all 32 systems inactive): the only gpuxtb
  kernels that launch are the always-on compaction/governance kernels
  (`prepare_solve_bucket_kernel`, `compact_solve_bucket_kernel`,
  `compact_successful_eigenpairs_kernel`; 10 instances = 5 replays x 2
  buckets). There are exactly **zero** graph-launched eigensolver kernels
  (`sytrd4`/`steqr`/`lae*`/`lansy*`) and **zero** TRSM kernels; the small
  remaining single-instance eigensolver kernels are the one-time overlap
  condition-number factorization from setup, not Graph replays.
- `nsys-active16-kern_sum.csv` (16 of 32 systems active, 8 per bucket): both
  buckets submit eigensolver and TRSM work — `batch_trsm_left_kernel`,
  `batch_trsm_right_kernel`, `gather_compacted_solve_bucket_kernel`,
  `symmetrize_compacted_bucket_kernel`, `validate_compacted_transformed_bucket_kernel`,
  `scatter_compacted_eigensystems_kernel`, and the cuSOLVER eigensolver
  (`sytrd4`/`steqr`/`lae*`/`lansy*`) all appear with 10 instances
  (5 replays x 2 buckets) plus the same one-time setup factorization.

### Capacity-tier cross-over (compacted Graph vs uncompacted full-capacity solve)

`compaction-crossover-summary.csv` contains every row. In microseconds
(mean over 50 samples), the largest tiers for each (batch, workload):

| batch | workload | active | compacted | uncompacted | crossing point (compacted wins below) |
| ---: | --- | ---: | ---: | ---: | --- |
| 1 | homog. n=32 | 1 | 859.6 | 849.7 | ~full |
| 1 | hetero n=16/40 | 1 | 386.5 | 402.9 | ~full |
| 8 | homog. n=32 | 1 | 863.6 | 868.6 | ~12.5% |
| 8 | hetero n=16/40 | 1 | 402.9 | 935.6 | 12.5% |
| 32 | homog. n=32 | 4 | 1008.2 | 873.0 | below active 4 (~12.5%) |
| 32 | hetero n=16/40 | 4 | 1676.3 | 1699.1 | ~12.5% |
| 128 | homog. n=32 | 4 | 1011.0 | 882.1 | below active 4 (~3.1%) |
| 128 | hetero n=16/40 | 4 | 1682.9 | 1755.8 | ~3.1% |
| 128 | homo/hetero any | 0 | 32-49 | 371-803 | empty tier 11.5-16.6x faster |

Interpretation, stated narrowly for this hardware (RTX 5090 sm_120), this
toolkit, and these synthetic sizes:

- The exact-capacity SWITCH Graph eliminates eigensolver/TRSM arithmetic for
  inactive peers (the active=0 tiers run in 0.03-0.05 ms vs 0.35-0.80 ms for
  the full-capacity solve, and the nsys node trace shows zero provider
  kernels), with correctness preserved at every tier.
- The compacted Graph carries a fixed SWITCH/Graph-replay dispatch cost that
  grows with the bucket capacity (the Graph contains one captured provider
  body per capacity level). Above the measured cross-over the uncompacted
  full-capacity solve is faster because all captured capacity bodies are
  instantiated even though only one is selected per replay. The measured
  cross-over lies at roughly 3-12% residual activity for batch 32/128 and
  roughly 12-25% for batch 8 on this workload set.
- Consequently, per-iteration exact-capacity compaction pays off in the tail
  of a heterogeneous mixed-convergence batch (a small number of peers still
  iterating), which is precisely the SCC regime where the loop keeps running;
  it should not be used blindly at high residual activity. A future
  capacity-tier design with fewer, coarser SWITCH bodies (for example
  power-of-two tiers) would shift the cross-over left, and the production
  loop integration must remain conditional-node-free because the device-tail
  loop graph (`gfn2_scc_loop.cu`) rejects conditional nodes for
  device-launch.

These are development measurements on synthetic buckets, not a release
claim: they cover the eigensolver component only (not the full SCC iteration),
one GPU, one toolkit, `n` 16/32/40, canonical active ordering, and the
uncompacted reference keeps the fixed topology count as the parallel path.

## Compute Sanitizer matrix (RTX 5090, CUDA 12.9.1, Compute Sanitizer 2025.2.1)

All runs executed the final committed binaries; exit codes and summaries are
verbatim from the sanitizer log files in this directory.

| Tool | Scope | Exit | Result |
| --- | --- | ---: | --- |
| memcheck | full `gpuxtb_cuda_eigensolver_test` (all compaction tests) | 0 | 0 errors |
| initcheck | full `gpuxtb_cuda_eigensolver_test` | 0 | 0 errors |
| memcheck | compacted Graph profile (heterogeneous 128, 64 active, 20 loops) | 0 | 0 errors |
| racecheck | compacted Graph profile (same) | 11 | 0 hazards displayed (0 errors, 0 warnings); tool does not terminate cleanly |
| synccheck | compacted Graph profile (same) | 11 | errors only inside NVIDIA cuBLAS `batch_trsm_left_kernel` launched via `cuGraphLaunch` |
| racecheck | direct (no-graph) uncompacted solve control | 0 | 0 hazards |
| synccheck | direct (no-graph) uncompacted solve control | 0 | 0 errors |

The `racecheck`/`synccheck` Graph-path findings are accepted as the same
NVIDIA Compute Sanitizer tool-boundary class recorded for issues #130/#140/#141
on this exact toolchain (conditional/Graph replay of cuBLAS/cuSOLVER batched
kernels): `racecheck` exits 11 while displaying 0 hazards, and `synccheck`
reports divergent-warp barriers inside NVIDIA `batch_trsm_left_kernel` /
`lansy_M_stage1` when those kernels are launched through `cuGraphLaunch`.
The direct-solve control runs the identical batched eigensolver/TRSM work
without a Graph and is fully clean under both tools (0 hazards / 0 errors),
which isolates the reports to Graph replay of these NVIDIA kernels rather than
to any gpuxtb compaction logic. No gpuxtb kernel appears in any finding, and
the non-waived gate for this evidence is the correctness + cross-over +
telemetry evidence above, not a waivable sanitizer claim.

## Limitations

The sanitizer log files are stored with trailing whitespace normalized only
(the pre-commit trailing-whitespace hook); their error/hazard summaries and
kernel attribution are preserved verbatim, and the SHA-256 manifest below
pins the normalized bytes.
- Synthetic homogeneous/heterogeneous AO buckets, not an end-to-end SCC run;
  the production SCC loop still uses the full-capacity eigensolver body, and
  the production-loop integration of an exact-capacity body is a separate
  open design decision bounded by the device-tail no-conditional-node
  constraint (documented in issue #131).
- `racecheck`/`synccheck` on the Graph path are tool-boundary findings, not a
  real-hazard claim; see the waiver record in Epic #1.
- Single machine, single toolkit, no Nsight Compute (perf-counter permission
  is admin-restricted on this host; kernel-level evidence uses Nsight Systems
  node tracing instead).
