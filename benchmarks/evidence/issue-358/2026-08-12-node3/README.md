# Issue #358: 62-atom Hessian displacement batching

This bundle measures one neutral-singlet C20H42 numerical Hessian on node3.
For xTBloom, batch size means displaced 62-atom systems per native force call,
not independent Hessians: one `186 x 186` Hessian requires 372 displaced force
systems, and batch 128 executes them as `128 + 128 + 116`.

## Result

All available rows used one warmup and five retained end-to-end samples. The
timing boundary is a complete public call through a host-visible binary64
Hessian. CPU processes were pinned to cores 0-15; BLAS was single-threaded.

| Engine | Displacement batch | Median | Retained range | Versus xTB | Correctness |
| --- | ---: | ---: | ---: | ---: | --- |
| xTB 6.7.1 native | n/a | 2493.262 ms | 2457.103-2568.318 ms | reference | pass |
| xTBloom CPU | 1 | 12814.535 ms | 12800.905-12848.488 ms | 5.14x slower | pass |
| xTBloom CPU | 128 | **1363.218 ms** | 1344.540-1536.321 ms | **1.829x faster** | pass |
| xTBloom CUDA | 1 | 25284.026 ms | 24815.993-25291.893 ms | 10.14x slower | pass |
| xTBloom CUDA | 128 | **2316.166 ms** | 2311.128-2362.553 ms | **1.076x faster** | pass |
| dxtb 0.4.0 CPU AD | n/a | 88614.586 ms | 88417.463-89232.416 ms | 35.54x slower | pass |

For this one workload and machine, displacement batching accelerated xTBloom
CPU by `9.400x` and CUDA by `10.916x`. CPU batch 128 was the fastest measured
row: `1.699x` faster than CUDA batch 128, `1.829x` faster than xTB, and `65.004x`
faster than dxtb CPU AD. CUDA batch 128 was `1.076x` faster than xTB and
`38.259x` faster than dxtb CPU AD.

These ratios do not establish a general CPU/GPU or cross-engine ranking. They
apply only to this generated 62-atom alkane, thread budget, hardware, SCC
policy, Hessian construction, and public timing boundary. In particular, dxtb
uses second-order automatic differentiation while xTBloom uses central
differences of analytic forces.

## Correctness

The common geometry is generated by `make_alkane(62)`, uses positions in bohr,
charge 0, no unpaired electrons, GFN2-xTB, and a 0.005 bohr displacement step.
The xTB native Hessian is the independent reference. Comparisons use the
symmetrized matrix because xTB symmetrizes its C-API result; raw xTBloom and
dxtb antisymmetry is retained separately.

Every available row was finite, repeatable, and below the `2e-3 Eh/bohr^2`
symmetry, acoustic, and cross-engine gates. Against xTB:

| Engine | Maximum absolute delta | RMS delta | Raw maximum antisymmetry | Maximum acoustic residual |
| --- | ---: | ---: | ---: | ---: |
| xTBloom CPU, both batches | 4.2183e-5 | 2.9761e-6 | 2.4382e-5 | 7.5617e-7 |
| xTBloom CUDA, both batches | 4.2183e-5 | 2.9761e-6 | 2.4382e-5 | 7.5617e-7 |
| dxtb CPU AD | 2.0133e-5 | 8.0746e-7 | 5.6332e-8 | 8.2419e-13 |

Values are in `Eh/bohr^2`. The compact JSON files retain every raw timing
sample and each Hessian's shape, dtype, byte count, and SHA-256 identity.

## Unavailable coordinates

- dxtb CUDA AD exhausted the RTX 5090: PyTorch reported about 31.09 GiB total
  process usage, 30.40 GiB allocated by PyTorch, and only 9.94 MiB free before
  the final failed 2 MiB allocation.
- dxtb CPU and CUDA numerical Hessians both raised
  `NotImplementedError: GFN2 not implemented yet.` The dxtb 0.4.0 numerical
  Hessian selects `forces_analytical` when present, while its GFN2 analytical
  force implementation is unavailable.
- dxtb does not support a batched Hessian API; its available AD result is one
  single-system Hessian.
- The isolated oneMKL provider is not used for the CPU result. Multi-worker
  context teardown can crash after successful compute; that separate provider
  defect is tracked by issue #360. CPU evidence here uses the verified LP64
  scipy-openblas32 provider.

file records the source raw filename, byte count, SHA-256, transformation list,

## Reproduction

Set `XTBLOOM_SOURCE_ROOT` to an absolute clean checkout of the measured
revision, then run the commands from that directory:

```bash
export XTBLOOM_SOURCE_ROOT=/absolute/path/to/xtbloom-hessian-benchmark
cd "$XTBLOOM_SOURCE_ROOT"
```

Fresh xTBloom builds used:

```bash
cmake -S . -B build/issue-358-evidence-cpu -G Ninja \
  -DXTBLOOM_ENABLE_CUDA=OFF \
  -DXTBLOOM_CPU_LINALG_LIBRARY=/home/jzzeng/miniconda3/lib/python3.13/site-packages/scipy_openblas32/lib/libscipy_openblas.so \
  -DBUILD_SHARED_LIBS=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build/issue-358-evidence-cpu --parallel 16

cmake -S . -B build/issue-358-evidence-cuda -G Ninja \
  -DXTBLOOM_ENABLE_CUDA=ON \
  -DCMAKE_CUDA_COMPILER=/group/software/cuda-12.9.1/bin/nvcc \
  -DCMAKE_CUDA_ARCHITECTURES=120 \
  -DXTBLOOM_CPU_LINALG_LIBRARY=/home/jzzeng/miniconda3/lib/python3.13/site-packages/scipy_openblas32/lib/libscipy_openblas.so \
  -DBUILD_SHARED_LIBS=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build/issue-358-evidence-cuda --parallel 16
```

Every measurement ran as one exclusive Slurm task with 16 requested CPU cores
and one RTX 5090. The command body used `taskset -c 0-15`; common xTBloom CUDA
environment was:

```bash

export PYTHONPATH="$XTBLOOM_SOURCE_ROOT/python"
```
